# Финансовый контракт v1

Статус: APPROVED. Утверждён техлидом 2026-11-15 на основе обоих ревью и решения пользователя «план/факт». Правило дневной стоимости обновлено 2026-11-21 по прямому запросу пользователя: [DV-8.md](DV-8.md).

## Граница якоря

Для факта хранить `effective_at` (RFC3339 UTC в хранилище), отдельный от CreatedAt, и монотонный ledger sequence. Якорь и запись факта сериализуются транзакциями с выделением sequence. При равных effective_at порядок определяется sequence. Факт после якоря определяется лексикографически `(effective_at, sequence) > (anchored_at, anchor.sequence)`. Старые якоря получают детерминированную исходную границу; нельзя объявлять старые планы фактами. Фактический ledger включает подтверждённые операции не позже Now. Показанный current/computed balance дополнительно автоматически учитывает остатки стоимости завершённых дней по DV-8.

При одинаковом времени legacy-факты располагаются перед legacy-якорем; исходный порядок фиксируется миграцией и сохраняется после повторного открытия.

Подтверждение сегодняшнего вхождения по умолчанию означает исполнение сейчас. Для прошлой даты default effective_at — 12:00 Europe/Moscow соответствующего дня. Можно передать явное время исполнения, не будущее и не раньше допустимой даты 0001-01-01. Оно может отличаться от исходной даты вхождения (перенос выплаты). Во фронтенде дата/время исполнения доступны явно; для сегодняшнего факта подпись поясняет, что он произойдёт после последней сверки. Чтобы указать расход, уже включённый в остаток, пользователь задаёт фактическое время до сверки. CreatedAt не используется как время исполнения.

Якорь не может быть в будущем. Новый якорь сохраняется как новая контрольная точка, не заменяет старые. При расчёте конца дня последний якорь внутри дня устанавливает остаток на свою границу; ранее подтверждённые факты до неё не применяются второй раз. Неизвестная история до первого якоря остаётся неизвестной.

## API

Префикс `/api/v1`. Денежные суммы — целые копейки, RUB.

Предел JSON денежных значений: абсолютное значение не больше 9007199254740991 (Number.MAX_SAFE_INTEGER). Ввод якоря/дневного бюджета неотрицательный, сумма операции положительная; вычисленный баланс может быть отрицательным. Все накопления/разности проверяют диапазон: переполнение не превращается в отрицательную или неточную сумму. Неверный вход → 400 VALIDATION_ERROR, переполнение вычисления → 409 CALCULATION_OVERFLOW без частичного результата. Mutation, которая делает фактический остаток непредставимым, должна откатиться. Непредставимые legacy-суммы выявлять без обрезания/округления, с явной ошибкой миграции.

### Категория

К существующему DTO добавить `system_code: "SALARY" | null`. У существующей default INCOME «Зарплата» сохранить UUID и установить SALARY. Новым пользователям создавать ту же системную категорию. Другие категории nullable.

### Вхождение

К существующему occurrence DTO добавить обязательные поля:

```json
{
  "event_id": "uuid",
  "occurrence_date": "2026-11-15",
  "status": "PLANNED",
  "effective_at": null,
  "counts_toward_day_budget": false,
  "series_deleted": false
}
```

Статусы: PLANNED, CONFIRMED, CANCELLED. Существующие kind, necessity, amount, category_id, comment сохраняются. Для факта они берутся из снимка факта, а не текущей серии. Для подтверждённого перенесённого вхождения календарь показывает запись в дне фактического исполнения, а occurrence_date остаётся первоначальной. Плановая запись в исходном дне второй раз не показывается/не начисляется. Facts подтверждённых вхождений, исчезнувших из правила после редактирования, всё равно возвращаются календарём.

`PUT /events/{id}/occurrences/{date}`. Пример тела:

```json
{"status":"CONFIRMED","effective_at":"2026-11-15T10:00:00Z","counts_toward_day_budget":false}
```

effective_at необязателен для CONFIRMED (default описан выше). Флаг резерва допустим только для расхода; default false. Возврат 200 и DTO вхождения. Повторный CONFIRMED возвращает существующий факт, если поля не изменены; отсутствие effective_at в повторе не сравнивается с новым Now. Несовместимый повтор с другой явной датой/флагом → 409 CONFLICT. Пара event_id + occurrence_date уникальна; конкурентные запросы создают один факт. Проверить валидность вхождения по recurrence и принадлежность пользователя в той же транзакции.

`{"status":"PLANNED"}` снимает подтверждение или отмену плана для существующей серии. Идемпотентно. Сначала искать сохранённый факт по первоначальному ключу: его можно снять и после изменения recurrence. Проверку соответствия текущему recurrence применять для создания нового факта/отмены, но не для снятия существующего факта. В ответ PUT добавить `plan_restored: boolean`: true, если после действия существует план по текущему правилу, иначе false. Если ключ факта исчез из правила, снять факт, но не выдумывать отдельный план. UI называет действие «Снять подтверждение», при plan_restored=false сообщает «Подтверждение снято. План не восстановлен: правило повторения изменилось». Для обычного PLANNED результат plan_restored=true. В календарном DTO поле не требуется.

`{"status":"CANCELLED"}` исключает неподтверждённое вхождение из прогноза; повтор идемпотентен. Для CONFIRMED → CANCELLED вернуть 409: сначала явно снять подтверждение. Нельзя подтвердить будущую исходную дату либо будущее effective_at. Перенос исполнения прошлой/сегодняшней исходной даты на другую небудущую дату допустим.

Удаление серии прекращает будущие планы и сохраняет факты (soft delete или эквивалент). У сохранённого факта series_deleted=true, UI не открывает редактор несуществующей серии. Изменения статуса для удалённой серии возвращают 409; удалять сохранённые факты вместе с серией нельзя. Редактирование существующей серии сохраняет снимки фактов и исключение их первоначальных ключей из планов.

404 для чужой/несуществующей серии или несуществующего вхождения (одинаковый ответ без раскрытия принадлежности), 400 VALIDATION_ERROR для неверной даты/статуса/будущего факта, 409 CONFLICT для несовместимого перехода.

### Календарь

`GET /calendar?from=YYYY-MM-DD&to=YYYY-MM-DD` всегда возвращает дни и операции, даже без якоря. `expected_balance` и `money_for_life` — Money | null. Остальные суммы дня известны (day_cost/income_total/required_total/optional_total) и не nullable. `summary` — прежний объект сводки либо null, если нет текущего якоря. В массиве events включить cancelled с явным статусом для возможности восстановления, но не учитывать их в totals и расчёте. cancelled показываются в исходный день.

Предельная длина диапазона — 366 дней включительно, ошибка валидации при превышении. Верхняя граница будущего календаря — Now + 3660 московских календарных дней; более далёкий диапазон отклоняется с VALIDATION_ERROR. Сводка не зависит от запрошенного видимого диапазона. API /balance и /forecast без якоря сохраняют 409 ANCHOR_REQUIRED.

Внутренняя работа также ограничена: нельзя материализовать все дни между далёким неизвестным прошлым диапазоном и текущим горизонтом. Запрос до первого якоря возвращает нужные дни/операции/null и обычную текущую сводку без обхода невидимого промежутка. Учитывать известные факты и якоря разреженно, дневные проекции строить для необходимых окон. Вычислительный budget/deadline служит дополнительной защитой.

### Сверка legacy

В /balance добавить `needs_balance_review: boolean`. Миграция отмечает существующих пользователей с якорями true; новые пользователи false. POST /balance/anchor сбрасывает признак. UI показывает неблокирующее пояснение «Расчёт обновлён. Сверьте текущий остаток» и действие сверки. Старые планы не превращаются в факты, строки и якоря не удаляются. Режим план/факт может изменить прежние расчётные цифры — баннер это объясняет.

До фиксации миграции v3 проверять не только отдельные суммы, но и накопленные фактические остатки всех исторических участков между якорями. Пример: якорь 9007199254740990 и последующий доход 2 должны дать явный отказ Open с rollback v3, сохранив исходные строки/суммы. Нельзя сначала зафиксировать непредставимую историю и затем требовать сверку, которую та же валидация отклоняет.

## Дневной резерв и история

counts_toward_day_budget — явный checkbox «Повседневная трата — из стоимости дня» при подтверждении расхода. Не привязывать автоматически к имени категории/необязательности. Факт уменьшает деньги, а остаток стоимости его дня равен max(стоимость дня − подтверждённые помеченные расходы этого дня, 0). Непомеченные факты не уменьшают этот остаток.

Стоимость завершённых московских дней автоматически уменьшает расчётный current/computed balance: от даты последнего якоря включительно до вчера включительно. Стоимость сегодня резервируется в прогнозе конца дня, после полуночи считается уже учтённой. Подтверждать день не нужно; при чтении не создаются фиктивные фактические операции. Помеченные расходы предотвращают двойное списание. Ручная сверка задаёт сумму сейчас и отсекает старые дневные оценки; день сверки учитывается после окончания дня. Исторический баланс на конец дня включает стоимость этого дня. Полное правило и примеры — DV-8.md.

История базовой стоимости дня содержит effective_from. UpdateSettings без отдельного поля даты меняет значение с сегодняшнего московского дня. Для legacy сохранить последнее известное значение как исходное известное значение (не выдумывать неизвестные старые изменения) и зафиксировать это ограничение. Overrides имеют приоритет. Для хранимых правил побеждает позднее созданное правило по внутреннему порядковому приоритету, независимо от одинакового времени и UUID; PUT сохраняет приоритет правила. Редактор дня создаёт новое однодневное правило. Для in-memory данных без приоритета допускается прежний deterministic fallback CreatedAt/ID.

Текущий прогноз начинается с расчётного остатка сейчас, уже уменьшенного на стоимость завершённых дней. Учитывает неподтверждённые планы сегодня и далее. Просроченные планы видны с датой/статусом; автоматически переносить их на сегодня или начислять нельзя. Плановое вхождение, исходная дата которого до последнего якоря, не начисляется повторно в прогнозе после якоря. Факт и неподтверждённый план на один occurrence key никогда не суммируются.

`money_for_life` сейчас = расчётный баланс с завершёнными днями + плановые доходы внутри горизонта − обязательные планы в нём − оставшийся резерв сегодня и последующих дней. Завершённые дни не резервируются второй раз. Необязательные планы отдельно в optional_remaining. `expected_balance` конца дня включает также необязательные планы. Для money_for_life на конец выбранного дня исходная сумма — expected_balance этого дня; резервирование начинается со следующего дня. После прошедшего горизонта money_for_life дня равен expected_balance (новое резервирование не производится).

Историческое money_for_life считается по текущим известным данным: после выбранного дня учитывать последующие подтверждённые факты, контрольные якоря (сброс остатка на их границе), оставшиеся допустимые планы и резерв. Пример: якорь D=10000, факт дохода D+1=8700, горизонт D+2, нулевой резерв → MFL дня D=18700. Следующий якорь внутри периода заменяет рассчитанный на его границе остаток. Снимки прогноза «как он был известен тогда» не восстанавливаются в v1.

NEXT_INCOME выбирает ближайшее неотменённое неподтверждённое будущее/сегодняшнее вхождение дохода в пределах 3660 дней от Now. Его день и само поступление исключаются из горизонта. Если сегодня всё уже подтверждено — искать следующее. Если доходов в доступном окне нет — конец текущего месяца. END_OF_MONTH/CUSTOM_DATE включительны. Custom date не дальше 3660 дней и не раньше сегодня при сохранении настройки; уже просроченная настройка вычисляет нулевой оставшийся период.

## Границы версии

Одно полное исполнение на вхождение; частичные оплаты не реализуются. Калькулятор ЗП заполняет существующую сумму без сохранения исходного расчёта. Изменение/удаление серии не является редактированием факта. Все ограничения видимы в UI там, где нужны для решения пользователя.

Создание новой операции сразу как факт состоит из POST события и PUT подтверждения. Фронтенд после успешного POST удерживает eventId и неизменное тело confirm. При неуспехе второго шага показывает «Операция создана как план; подтверждение не завершено»; повторяет только идемпотентный PUT, не создаёт второе событие. При неопределённом сетевом результате подтверждения повторяет тот же payload. Если пользователь отменил продолжение, существующий план остаётся доступен в календаре.
