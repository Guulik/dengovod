# ТЗ: бэклог #1–4 и необходимые исправления

## Принятые продуктовые правила

Пользователь подтвердил разделение «план/факт». План не меняет текущий остаток. Подтверждённый факт меняет его один раз. Статус относится к паре `event_id + occurrence_date` (исходная дата повторения), а не ко всей серии. Повторное подтверждение идемпотентно. Будущий факт запрещён. Отмена подтверждения возвращает план и не создаёт вторую операцию. Редактирование серии сохраняет уже подтверждённые суммы и даты; нельзя незаметно переписать факт.

Якорь — фактически доступная сумма в указанный момент. Предшествующие факты уже включены в неё. Введённая задним числом операция не меняет следующий подтверждённый якорь. Для совпадающих времён нужна детерминированная граница; нельзя выбирать её по случайному UUID. Подтверждение по умолчанию означает исполнение сейчас для сегодняшнего вхождения; для прошлой даты нужна явная финансовая дата, а не CreatedAt. Точная схема границы и DTO фиксируются техлидом после предложения reviewer в CONTRACT.md.

Календарь показывает прогноз на конец дня, текущий баланс — факт на текущий момент. До первого якоря баланс неизвестен (`null`), но операции, даты и CRUD доступны. История считается по участкам между якорями. Установка остатка сегодня не переписывает известный баланс вчера.

Базовая стоимость дня — резерв обычных повседневных трат в прогнозе, а не автоматически созданный факт. Фактическая повседневная трата уменьшает остаток дневного резерва до нуля; специальные обязательные расходы не должны произвольно поглощать этот резерв. Точное маркирование фиксируется в CONTRACT.md. Новое значение стоимости дня действует с даты изменения, не переписывая более ранние значения. Overrides сохраняют приоритет; одинаковое время создания разрешается детерминированно.

Прогнозный остаток = фактическая исходная сумма + последующие факты + неподтверждённые планы доходов − неподтверждённые планы расходов − остаток дневного резерва. Подтверждённый план не учитывается второй раз. «Деньги на жизнь» = факт сейчас + плановые доходы в горизонте − обязательные планы − остаток дневного резерва. Необязательные планы показываются отдельно. Для дня на конец дня резервировать только последующие дни. У каждой метрики один алгоритм во всех endpoints; календарный день и сводка могут отличаться только моментом расчёта.

Горизонт NEXT_INCOME — ближайшее ожидаемое вхождение дохода; подтверждённые и отменённые пропускаются. Сам граничный доход и его день исключаются из резерва. Сегодняшний ещё ожидаемый доход остаётся допустимой границей. END_OF_MONTH/CUSTOM_DATE включают последний день. Прошедший custom horizon не создаёт отрицательных периодов.

## Backend: A-1 и #1/#3/#4

- Последовательные SQL-миграции с версионированием, транзакцией на миграцию, безопасным распознаванием старой базы. Повторный Open не изменяет данные. Ошибка миграции не оставляет половину изменений. Пользовательскую базу для экспериментов не использовать.
- Модель подтверждённого вхождения и идемпотентный API с проверкой принадлежности пользователю и валидности вхождения. Нет подтверждения чужого/несуществующего вхождения.
- Несколько якорей, неизвестная история и корректный endpoint календаря без якоря. balance/forecast могут возвращать ANCHOR_REQUIRED, но calendar должен возвращать операции и nullable расчёты.
- Версионирование базового дневного резерва и стабильная системная идентичность категории зарплаты (`system_code: SALARY`, nullable для прочих). Действующие категории сохраняют UUID.
- Единый финансовый расчёт. Обход дней и вхождений без квадратичного пересчёта каждого будущего дня. Сводка не должна строить 3660 дней без необходимости. Ограничение API-диапазонов и отмена запроса.
- Автор пишет содержательные unit/repository/API тесты, включая обновление существующей схемы с пользовательскими данными.

## Frontend: A-2 и #1/#2/#3

- Все финансовые query keys привязаны к текущей сессии/пользователю; при выходе и смене сессии отменить старые запросы и очистить приватные данные/выбранные сущности. Поздний ответ и mutation из старой сессии не раскрывают данные и не портят новую сессию.
- Календарь сохраняет выбранный месяц при загрузке и обновлении. Начальная загрузка сводки не блокирует работу с датами; прошлые даты доступны с первого входа. Неизвестная сумма отображается «—», не 0.
- Статус «План»/«Факт» виден в деталях дня. Действие подтверждает только выбранное вхождение. Во время запроса повторное действие блокируется, ошибка понятна, успешное действие обновляет баланс, календарь и горизонт. Для новых прошедших/сегодняшних операций можно явно выбрать факт; будущие только план.
- Не спутывать подтверждение вхождения с редактором всей серии. Подтверждённые суммы не меняются от редактирования серии. Входные/выходные схемы строго соответствуют CONTRACT.md.
- Все даты предметной области Europe/Moscow; date-only строки не преобразовывать через UTC-парсинг со сдвигом дня. Навигация календаря использует календарные даты и не должна смещать выбранный день.

## #2: зарплатный калькулятор

Появляется для дохода в системной категории SALARY; для старого API допустим явно описанный временный fallback по дефолтной категории «Зарплата», который затем убирается после интеграции system_code. Формула: оклад в копейках × число уникальных отработанных календарных дней / число календарных дней выбранного месяца. Промежуточные результаты не округлять, итог до копейки по half-up. Проверять допустимость safe integer/переполнение.

Два способа ввода: целое число от 0 до длины месяца или выбор уникальных дат внутри месяца. Переключение режима не создаёт несовместимое скрытое значение. Февраль 28/29, 30 и 31 день покрываются тестами. Неверный оклад, дробное/отрицательное/слишком большое число дней, даты вне месяца дают ошибку. 0 отработанных → расчёт 0, но сохранить нулевую финансовую операцию нельзя.

Результат применяется к полю суммы только явной кнопкой. Пользователь может затем изменить сумму вручную. Дата выплаты остаётся датой операции и не меняется при выборе расчётного месяца/дней. Калькулятор является помощником ввода: сохранённая операция содержит итоговую сумму; сохранение исходной формулы в этой версии не требуется. Этот факт объяснить короткой подсказкой. Календарный знаменатель явно подписан, расчёт не выдаётся за расчёт по производственному календарю.

## Независимая приёмка QA

1. После регистрации доступна прошлая дата, создание, просмотр, изменение и удаление операции; баланс до первого якоря неизвестен.
2. Якорь 10 000, вчерашний факт 1 500 → сегодня 10 000. Повторное сохранение текущего остатка не меняет его.
3. План дохода сегодня 8 700 → факт сейчас прежний, прогноз учитывает 8 700; подтверждение даёт +8 700 один раз; завтра прогноз сохраняет доход. С дневным резервом 400 ожидаемое уменьшение только на соответствующий резерв, без потери дохода.
4. Повторное/конкурентное подтверждение не удваивает сумму. Подтверждение одного месяца не подтверждает остальные. Чужой пользователь не может менять вхождение.
5. Исправление прошлого факта не меняет остаток после следующего якоря; новая сегодняшняя сверка не переписывает прошлый известный день.
6. План обязательного расхода/подтверждение/отмена не списываются дважды. Дневной резерв не меняет фактический баланс автоматически.
7. После сегодняшнего факта дохода горизонт переходит к следующему ожидаемому доходу.
8. Изменение дневной стоимости не переписывает прошлые дни. Сводка и календарь используют общую финансовую модель.
9. Профиль A → выход → B: ни финансовые суммы, ни категории, ни выбранные сущности A не видны B, в том числе при задержанном ответе.
10. Месяц вперёд/назад остаётся выбранным при сетевой задержке и mutation. Календарь и калькулятор удобны на ширине 390px.
11. Зарплата: 100000 ₽ × 15 / 30 = 50000 ₽; високосный февраль; округление; оба режима ввода; дата выплаты неизменна.

QA пишет собственные сценарные тесты в отдельных файлах, не просто повторяя структуру реализации. e2e по возможности работают с настоящим API и отдельной временной SQLite-базой. Mock-only тесты не называются e2e. Все пропуски и ограничения записываются в отчёте.
